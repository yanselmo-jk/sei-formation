🔴 **U56-2(끝단 인증 2건 + 시도 3건)는 U-56a 게이트를 세우기 위한 첫 실측 시도입니다.** 시도가
반드시 성공한다는 뜻은 아닙니다 — TS(전이상태) 탐색은 실패도 데이터이며, 실패해도 왜 실패했는지
회신에 남습니다. 각 시도는 자신의 끝단 인증이 실제로 수렴(n_imag=0)해야만 DFT 계산을 시작합니다
(C-8 안전장치) — 끝단이 아직 인증되지 않았다면 그 시도는 core-h 를 거의 쓰지 않고 즉시 거부됩니다.

> **예약(천장)과 예상 소비는 다른 숫자입니다.** 예약은 `코어 × wall × 링크` 로 계산한
> **넘을 수 없는 상한**이고(스케줄러가 강제), 실제 청구는 **쓴 만큼**입니다.
> PBS 는 요청한 wall 이 아니라 **실사용**을 과금하므로 미사용분은 청구되지 않습니다.

계획 표에 이런 표시가 보이실 수 있습니다:

```
probe_queuewait  RUN  etc  21  0.03  1  44.8  큐 대기 실측  ⚠ [64] node 생략(상한 16)
```

> **뜻**: 큐의 노드 수 상한을 저희가 모르는 동안, **64노드 요청은 보내지 않았습니다.**
> 큰 잡이 거부되면 큐 대기 측정이 통째로 0이 되기 때문입니다. 실제로는 **1 / 4 / 16 노드**
> 세 개만 나갑니다(그래서 `21 = 1+4+16`). **이 생략 사실은 회신 JSON 에도 기록됩니다.**
> 64노드도 재고 싶으시면 `config/sizing.json` 의 `max_probe_nodes` 를 올려 주세요.

## 🔴 제출 전에 멈춰야 하는 경우 — **wall 상한이 48시간이 아닐 때**

이 패키지는 `qstat -Qf` 로 큐의 wall 상한을 **직접 읽습니다.** 저희 계획은
**`normal` 큐 = 48시간**을 전제로 세워져 있습니다.

```
🔴 큐 `normal` 의 walltime 상한이 24.0 h 다 — 확인해 준 값 48.0 h 와 다르다
🔴 큐의 wall 상한을 확인하지 못했다 [UNVERIFIED]
```

> **둘 중 하나가 뜨면 제출하지 마시고 알려 주세요.**
> 저희 잡 크기·분할 수가 전부 48시간 위에서 계산돼 있어서, 상한이 더 짧으면
> **가장 큰 잡(P1)이 시간 초과로 잘립니다.** 그러면 왕복 한 번이 통째로 낭비됩니다.
> (상한이 더 짧아도 저희가 자동으로 맞추긴 합니다. 다만 **일부 항목이 실행에서 빠질 수
> 있고**, 그 사실이 화면에 크게 표시됩니다 — 그때도 알려 주세요.)

## 필요한 것

`python3`(3.6+) 하나뿐입니다. `pip install` 도 인터넷도 필요 없습니다.

* **Gaussian16** — P1 / P1b / P5 / P6 가 씁니다. `PATH`, `$g16root`, 그리고 **`module avail` 에
  보이는 후보를 실제로 `module load` 해 보는 것**까지 시도합니다. 찾으면 그 모듈 이름을
  잡 스크립트가 **계산 노드에서도** `module load` 합니다.
* **xtb** — 동봉돼 있습니다(아래 참조). 설치 불필요.
* **CP2K** — 계산에는 쓰지 않습니다. `probe_node` 가 **설치 여부만 기록**합니다
  (뒤 단계의 대비책 판단용). 없어도 아무 항목도 생략되지 않습니다.

**설치하지 마세요.** 없는 소프트웨어는 "없음"이 그 자체로 저희에게 필요한 답입니다.
모듈 시스템을 쓰시면 패키지 루트에 `modules.conf` 를 만들어 두시면(`module load ...`)
모든 잡이 먼저 읽습니다.

### 동봉된 `xtb` (약 19 MB — tarball 이 큰 이유)

* 버전 6.7.1. 출처·SHA256·라이선스는 `vendor/xtb/PROVENANCE.json`.
* LGPL-3.0-or-later (`vendor/xtb/COPYING.LESSER`). 재배포 조건을 지킨 형태입니다.
* 시스템에 `xtb` 가 있어도 **동봉본을 우선** 씁니다(저희가 검증한 버전으로 재현성을 맞추려고).
* 동봉본이 실행되지 않으면(glibc 등) **사유를 기록하고** 시스템 `xtb` 로 넘어갑니다.

### 계산 레벨

기본은 **G-1** (wB97XD / def2-TZVPPD / SMD). 이 기저는 Gaussian 내장 키워드가 아니라서
패키지가 기저 파일을 동봉하고 `gen` 으로 넣습니다(`inputs/basis/`).
더 싸고 빠른 회신을 원하시면: `./run.sh --level g2` (def2-TZVPD)

## 중간에 끊겨도 괜찮습니다

* wall 제한에 걸려 잘려도 **이어서 돌 잡이 제출 시점에 이미 예약**돼 있습니다.
* **같은 디렉터리에서 `./run.sh` 를 다시 실행하시면 실패한 항목만 다시 돕니다.**
  이미 성공한 항목은 건너뜁니다 — 다시 계산하지 않습니다.

### 특정 항목을 처음부터 다시 돌리고 싶을 때

```bash
./run.sh --rerun P5            # (여러 개면 --rerun P5 --rerun P1b 처럼 반복)
```

* 지정한 항목의 상태 마커를 `<이름>.reset.<시각>` 으로 **옆으로 치우고**(삭제하지 않습니다)
  그 항목만 다시 제출합니다. 무엇을 치웠는지 화면에 그대로 출력됩니다.
* 🔴 **완료된 항목은 `--force` 로는 다시 돌지 않습니다.** 성공한 계산을 실수로 다시 돌려
  core-h 를 태우는 사고를 막기 위해, 완료 항목의 재실행은 반드시 `--rerun <이름>` 으로
  이름을 지정해야만 됩니다.
* 항목이 "제출됐으나 스케줄러에 없음(외부 종료 추정)" 으로 표시되면 — 잡이 `qdel` 등으로
  밖에서 종료된 것입니다. 자동으로 다시 제출하지 않으니, 다시 돌리시려면 위의
  `--rerun <이름>` 을 쓰시면 됩니다.
* 마커 파일을 손으로 지우실 필요는 없습니다 (지우지 말아 주세요 — `--rerun` 이 정규 경로입니다).

## 문제가 생기면

무엇이 실패해도 **다른 항목은 계속 진행**되고, 실패는 리포트의 `failures[]` 에 사유와
로그 일부가 함께 기록됩니다. **실패한 채로 회신해 주셔도 매우 유용합니다** —
오히려 그것이 알고 싶은 것입니다.

### 제출이 거부되면

거부 메시지가 **전문 그대로** 화면에 나옵니다. **잘라서 보내지 말고 그대로 회신해 주세요** —
원인이 뒷부분에 있는 경우가 많습니다. 그리고 저희가 정확히 무엇을 보내는지 함께 보여 주세요:

```bash
./run.sh --emit-script probe_node     # 제출 스크립트 전문 (실제 제출본과 동일합니다)
```

이 둘이면 대개 한 번에 원인이 확정됩니다.

| 증상 | 대처 |
|---|---|
| `ncpus` 값을 사이트가 제한한다 | `./run.sh --ncpus-per-node 32` |
| 큐 이름이 다르다 | `./run.sh --queue <이름>` (기본 `normal`) |
| 계정이 다르다 | `./run.sh --account gaussian=<이름>` (소프트웨어별) 또는 `--account <이름>`(전체) |
| 계정이 원인인지 보고 싶다 | `./run.sh --dry-run --account vasp` 로 돌려 `제출 사전검사` 줄을 비교 |

⚠ **PBS 에서 사전검사는 완전 무부작용이 아닙니다.** `sbatch --test-only` 같은 명령이 PBS 에
없어서, `qsub -h`(보류 상태로 제출) 후 즉시 `qdel` 하는 방식을 씁니다. **잡 ID 를 하나 쓰고
회계 로그에 남습니다.** 삭제가 실패하면 잡 ID 를 크게 알려 드리니 `qdel` 해 주세요.
사전검사를 끄시려면 `./run.sh --no-precheck`.
(사전검사는 **실제로 제출될 것과 같은 스크립트**를 검사합니다.)
